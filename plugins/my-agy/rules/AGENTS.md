- 必ず `compact` と `i-have-adhd` を使用する。両スキルは `view_file` で読み、従うこと
- 私の要求に迎合せず、メタ認知でクリティカルシンキングで対応すること
- 許可なくフォールバックなどで意図しない対応をしないこと

## 開発

- `GIT_CONFIG_GLOBAL=/dev/null` は禁止
- 実装には `ponytail` を使用する
- DRY、KISS、YAGNI を意識する
- `rg` では表現できない構文認識パターンには `ast-grep` を使用する
- 明確な原因が特定されるまでは無理に修正しない
- 人間のレビューがされていない変更はコミットしない

実装後はセルフレビューを行い、関連するチェックを実行すること。
レビューまたはチェックで明確な問題が見つかった場合は修正し、影響を受けるレビューまたはチェックを再実行すること。
最新の確認で対応すべき問題がなく、検証が通るまで繰り返すこと。
レビューでは無関係な改善や推測に基づく改善は追求しないこと。

## セルフレビュー

一般的なレビュー項目と、以下について確認する。

- 要件
  - 要求された振る舞いを満たしているか
  - 要求外の振る舞いを追加していないか
- 正しさ
  - 変更に関係する境界条件、異常系、状態遷移で破綻しないか
  - テストは指示に従っているか
  - アーキテクチャに則っているか
  - YAGNI、DRY、KISSに則っているか
  - ファイルの配置場所は問題ないか
  - ライブラリの使用は検討したか
- 影響
  - 呼び出し元や関連処理の既存の契約を壊していないか
  - 今回の要件に不要な分岐、抽象化、依存、変更がないか

## ドキュメント

- システム全体の背景、設計判断、使い方、運用を書く
- リポジトリのドキュメントにメモや未決定事項を書かない
- 短く、要点を絞り、重複させない
- まだドキュメントにできない固まっていない事項は、認知負荷の高い長文ではなく `show-me` を使用する
- Denを使っている場合は `den-show-me` を使用する

## テスト

- 意味のある振る舞い上の契約を保護できる、最小限で重複しない本質的なテストにする
- 偶発的な実装詳細や一度きりの再現値が契約の一部でない限り、それらを固定せず一般化する
- 固有名詞や個人情報を含めない

## ツール

- `mise`、`just`、`uv`、`vp` を積極的に使う
- 常にシェルコマンドの先頭に `rtk` を付ける。ただし `justfile` の中身には付けない

Python製の検証ツールに依存パッケージが不足している場合は、システムのPythonへインストールせず、
`uv run --with <package> --no-project ...` の形式で実行する。
