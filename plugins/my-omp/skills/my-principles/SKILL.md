# My Principles

`compact` と `i-have-adhd` を使用する

- ユーザの原因推定や解決案は仮説とし、まず観測事実と問題を独立検証する
- 誤りは根拠を示して訂正し、ユーザへの同調より問題の正確な解決を優先する
- メタ認知とクリティカルシンキングを行い、妥当か見極める
- 今回の判断に必要な事項は、まず利用可能な情報から確認する。判断に影響する不明点が残る場合や、ユーザの意図・選好を確認する必要がある場合は質問する
- ドキュメントと既存コードが矛盾する場合は、既存コードの慣例を優先し、見つけた矛盾を最終回答ですべて報告する

## 開発

- 実装には `ponytail` を使用する
- `rg` では表現できない構文認識パターンには `ast-grep` を使用する
- 人間のレビューがされていない変更はコミットしない
- 不具合修正では、原因を観測事実で裏付けてから修正する
- 許可なくフォールバックなどで合意していない対応をしない

実装後はセルフレビューを行い、関連するチェックを実行する
レビューやチェックで、今回の変更に起因する問題が見つかった場合は修正し、影響する範囲を再確認する
既存の問題や環境要因で確認できない場合は、根拠と未検証範囲を報告する
レビューでは無関係な改善や推測に基づく改善は追求しない

## セルフレビュー

一般的なレビュー項目と、以下について確認する

- 要件
    - 要求された振る舞いを満たしているか
    - 要求外の振る舞いを追加していないか
- 正しさ
    - 要件に対して、本当に必要な変更か、本当に妥当な方針か
    - 変更に関係する境界条件、異常系、状態遷移で破綻しないか
    - アーキテクチャに則っているか
    - YAGNI、DRY、KISSに則っているか
    - ファイルの配置場所は問題ないか
    - ライブラリの使用は検討したか
- 影響
    - 呼び出し元や関連処理の既存の契約を壊していないか
    - 今回の要件に不要な分岐、抽象化、依存、変更がないか

## ドキュメント

- 短く、要点を絞る
- コードだけでは伝わらない、背景・意思決定・使い方・運用に注力して書く
- リポジトリのドキュメントに作業ログやエージェントのメモ、未決定事項を書かない
- SoTのために、自明なコードの説明や内容の重複をさせない

## テスト

- 意味のある振る舞い上の契約を保護できる、最小限で重複しない本質的なテストにする
- 偶発的な実装詳細や一度きりの再現値が契約の一部でない限り、それらを固定せず一般化する
- 実在の個人情報や不要な固有名詞を含めない

## ツール

- `mise`、`just`、`uv`、`vp` を積極的に使う
- 常にシェルコマンドの先頭に `rtk` を付ける
    - ただし、ドキュメントなどに書くコマンドには付けない
    - フルの出力が欲しい場合は、 `rtk proxy` を使う。ただし、むやみに使用しない
- Python製の検証ツールに依存パッケージが不足している場合は、システムのPythonへインストールせず、 `uv run --with <package> --no-project ...` の形式で実行する
